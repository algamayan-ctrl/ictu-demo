## Requirements and design before application revisions

Objective: verify and repair only demonstrated gaps in an actual external off-campus SAO Return for Revision → owner correction → corrected E-sign resubmission, preserving reviewed affiliation, signed history, correct reviewer responsibility and zero premature inventory allocation.

Confirmed sources: explicit user authorization; final workflow DOCX body paragraphs P26/P28/P33/P36/P48 (applicable letter/PTC, acknowledgement, deliberate E-sign and retained record), P52 (SAO correction remarks, borrower notice, editing/resubmission, SAO before Admin for off-campus) and P56 (Admin queue after SAO verification). Paragraphs here use zero-based body paragraph indexes from direct read-only XML extraction. Manuscript XP/BPR, records/audit traceability and separate operational KPI foundations continue. Existing ZIP design and shared controls must be retained.

Actors/permissions and stories: approved, active, email-verified External Borrower edits only its own returned request and signs the correction; current SAO records correction instructions and reviews the corrected off-campus version; Admin retains final authority but cannot decide before current-version SAO verification; ICTU and unrelated borrowers cannot perform either operational action. Rejected/pending/inactive accounts and revoked staff access remain blocked by existing gates. SAO return-for-revision does not grant approval or require a positive verification signature.

Preconditions: existing signed off-campus version with readable private applicable documents, pending sequence-1 SAO step, approved external registration and no allocation. Postconditions: original version/signature/files retained; correction creates one new unsigned version, then one owned immutable E-sign snapshot at resubmission; applicable fresh documents belong to that new version; current sequence-1 SAO step only; corrected request re-enters SAO and remains outside Admin approval responsibility until verified.

Business rules: require meaningful SAO remarks; do not copy prior approved letter/PTC automatically into a new version; letter always required and PTC conditional on the existing student-activity flag; preserve the request's reviewed company snapshot and null CSPC accountable unit/division/office; never derive an external CSPC assignment from client fields. Existing current-premises routing remains: this test cycle stays off-campus; no new rule forbids changing premises or other allowed request details. Missing/corrupt/private-file/signature checks and explicit acknowledgement apply again. Existing request date/catalog restrictions remain; synthetic dates/items are not institutional opening balances or new eligibility rules.

Inputs/outputs: existing decision, remarks, corrected request/item/date fields, fresh uploaded letter/PTC, acknowledgement and owned E-sign consent. Outputs: validation/403 on failures; actionable correction remarks/notice; saved unsigned correction or signed resubmission; proper queues/audits. No schema migration proposed. Existing request_versions, request_supporting_documents, signature_snapshots, approval_steps, notification_events/deliveries, status_history and audit_events are involved. Allocations/custody/official operational documents must remain absent in this gate.

States: signed UNDER_SPMU v1/sequence1 RECEIVED → RETURNED_FOR_REVISION v1/sequence1 returned → DRAFT v2 unsigned → UNDER_SPMU v2/sequence1 RECEIVED. Prior v1 step/doc verification records the SAO's decision; signed bytes and request/company evidence remain. A failed atomic edit-and-submit must restore returned v1 and remove only newly created private files/metadata. A saved unsigned v2 may be edited again without creating v3; repeated/stale signing or decision must not duplicate or act on a superseded correction.

Exceptional cases/test acceptance: successful actual endpoint cycle with/without conditional PTC; empty/oversized remarks; wrong actor/owner/reviewer, revoked roles and early Admin decisions; signing old returned version; missing corrected letter/PTC, invalid consent and corrupt evidence; saved-draft/resume; registration company/client assignment changes cannot rewrite snapshot; audit/storage failure rolls back state/documents/notifications and newly written files; stale reviewer race and repeated correction/submission do not mutate the new version; parallel correction when applicable. Verify audits/recipient scope/byte integrity and database consistency at every stage.

Existing implementation: ApprovalController::verify → RequestWorkflowService::verifyByActionOfficer already marks current documents returned, transitions/notifies/audits without allocating. BorrowingRequestController::update locks the header, creates a new version from a returned request, preserves company via BorrowerRequestAffiliationService, saves new documents, and atomically submits on intent=submit. Submission locks/refetches, validates evidence and signatures, routes by current premises, and creates only the current reviewer step. Middleware and signature/file services track new private files for rollback. Current services reload versions under locks; stale cross-version reviewer behavior still needs a negative test before deciding on any fix.

Dependencies/risks: observed PHP 8.4.26/Laravel 13.25.0/PHPUnit 12.5.33, isolated SQLite/MariaDB 11.4 testing, separate file/Blade caches and synthetic readable PDFs/PNG. The existing preview must be preserved. Missing hosting/ICTU/inventory/KPI attachments, broader P50 informational notice recipients, official approval-versus-preparation document-generation timing, Google domains/OAuth, external account editing, cancellation and analytics increments remain separate. No new approval authority, fee/date/sanction policy, production migration/reset, deployment or reference edit is authorized here.

Implementation sequence: add actual-endpoint regression first; retain before/after logs; change only demonstrated gaps; run focused and affected account/routing/document/notification regression on both engines, frontend checks and browser correction flow; inspect source identity and retained evidence; update progress/steps and record gate decision. ## Verification evidence

Baseline: the actual cycle and most negative cases already work (18/20 initial cases passed). One expected-403 assertion was a fixture/harness mismatch: the existing duplicate-action middleware legitimately redirects a completed retry; a cache-cleared repeat independently checks the controller's 403 boundary. The first discovery run also had a helper named head() conflicting with Laravel's HTTP test method; it was renamed and that failed run is retained, not reported as a behavior result.

The stronger six-case defect baseline passed three and failed three: (1) a route-bound/preloaded SAO v1 action returned newly resubmitted v2, (2) an old browser form's reviewed version was ignored and returned v2, and (3) a failed SAO decision audit still attempted one borrower HTML email despite database rollback. Mail::fake() does not reliably count the application's Mail::html call, so the revised test instruments that call directly without real email delivery. Evidence: route2a-baseline.txt and route2a-defect-baseline.txt.

Small corrections authorized by these defects: compare the bound version number again under the existing request lock; send the rendered SAO form's reviewed_version_id and compare it to the locked current version; retain the service's existing five-argument callers and legacy clients by making this identity parameter optional, while rejecting any supplied mismatch. The identity is a consistency check, not role authority. Record the correction audit before dispatching its notice, so a known audit failure produces no misleading mail attempt. This does not introduce an outbox or certify rollback of every possible later transport/commit failure; broader notification delivery hardening remains separate. No migration, layout rewrite or business-state change.

Browser-discovered scope extension: the returned form shows old document previews and treats those documents as already uploaded for submit readiness. With acknowledgement and no new files, it enables E-sign & Submit, despite the server correctly requiring fresh documents for a new version. Correct only readiness sources and wording: retained links are Previous version; old returned documents never satisfy either JS submit path; saved current-draft documents still satisfy their own version. Existing colors/icons/spacing and backend validation remain. Add two actual-return rendered-form cases (regular/student activity), retain their failing baseline, then verify letter-only blocks for PTC and both fresh uploads enable the corrected submit in the browser.
